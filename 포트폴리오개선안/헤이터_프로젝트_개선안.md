## 잘 된 것

- **세션 복구**: 문제 발생 → 해결 → OCP 위반 인식 → Dictionary 리팩토링까지 사고 과정이 명확하게 서술되어 있다.
- **Singleton CRTP**: 왜 제네릭 베이스 클래스인지, 왜 CRTP 패턴인지 판단 근거가 있다.
- **WebGL 최적화 수치**: 드로우콜 3500→180, 메모리 60mb→15mb로 before/after 수치가 명확하다.
- **SpriteSync 비교 표**: 4가지 방식 비교 표가 있어 기술 선택 근거가 시각적으로 드러난다.
- **초기 기획 변경점**: 기획 문서 링크와 변경점 표를 통해 기획-개발 연결고리가 보인다.

## 개선 사항

### 1. 담당 역할 표 추가

6인 팀 프로젝트인데 본인이 어떤 부분을 담당했는지 한눈에 보이지 않는다. 각 섹션을 읽어야만 기여 범위를 파악할 수 있는 구조다. 탐사 컨텐츠처럼 전체 중 일부를 담당한 경우 비중도 함께 명시해야 한다.

```
| 역할 | 비중 | 내용 |
| 아키텍처 설계 | 본인 | Thread safe Singleton 제네릭 베이스 클래스 |
| 세션 관리 | 본인 | 새로고침 대응 세션 복구 시스템 |
| 디펜스 기능 | 본인 | 유닛 배치·사정거리 인디케이터·오브젝트 풀 스폰 등 |
| 탐사 컨텐츠 | 본인 (N종 중 4종) | 기근·마력 안개·인사 이동·저주 정화 이벤트 구현 |
| 보안 | 본인 | AES-GCM + RSA 기반 암호화 통신 구현 |
| 최적화 | 본인 | GPU Instancing·SpriteSync·텍스처 설정으로 WebGL 개선 |
```

---

### 2. 코드 공개 관련 안내 추가

SSAFY 팀 프로젝트이므로 전체 소스코드를 외부에 공개할 수 없다는 사실을 명시해야 한다. 별도로 설명하지 않으면 GitHub 링크가 없는 이유를 독자가 알 수 없다. 문서 말미에 짧게 한 단락으로 추가하면 된다.

---

### 3. 스폰 시스템 — 수치 추가

"300마리~1500마리"라는 규모를 언급하면서 풀링 적용 전후의 수치가 없다. WebGL 최적화 섹션에서 드로우콜·메모리 수치를 제시한 것처럼 여기에도 GC 스파이크나 프레임 수치 등 정량적 근거가 있어야 구현의 필요성이 설득력을 갖는다.

---

### 4. 암호화 통신 — 기술 선택 비교 추가

현재는 AES-GCM을 적용했다는 설명과 코드만 있다. "왜 대칭키인가", "왜 RSA로 세션키를 교환하는가"에 대한 선택 근거가 없다. SpriteSync 섹션에 이미 4가지 방식 비교 표가 있으므로 동일한 포맷을 여기에도 적용하면 일관성이 생기고 설계 판단력도 드러난다.

```
| 방식 | 암복호화 속도 | 키 노출 위험 | 채택 여부 |
| 평문 전송 | — | 높음 | ✗ |
| 비대칭키 단독 (RSA) | 느림 | 낮음 | ✗ |
| 대칭키 단독 (AES) | 빠름 | 높음 (키 교환 문제) | ✗ |
| AES-GCM + RSA 세션키 교환 | 빠름 | 낮음 | ✓ |
```

---

### 5. 기근·인사이동·저주정화 섹션 — 판단 근거 보강

세션 복구와 WebGL 최적화는 "왜 이 방법을 선택했는가"가 명확하게 서술되어 있다. 반면 아래 세 섹션은 구현 방식 설명에 그쳐 수준 차이가 있다.

- **기근**: 저장/로드 시점을 일원화했을 때 방지되는 버그 시나리오를 구체적으로 서술해야 한다. "새로고침 시 횟수 차감 없이 식량이 소비되거나, 식량 소비 없이 횟수가 차감되는 상황을 방지"처럼 한 줄이면 충분하다.
- **인사 이동**: 코드만 있고 "왜 이 방식으로 구현했는가"가 없다. 클램프 처리를 넣은 이유 등 판단 근거가 한 줄이라도 있어야 한다.
- **저주 정화**: "로그 분석을 통해 알 수 있었다"는 서술이 있는데 분석 결과가 없다. 어떤 웨이브 조합에서 위험도가 어떻게 달라졌는지 수치나 사례가 있으면 좋다.

---

### 6. 탐사 컨텐츠 — 담당 범위 명확화

"일부 구현"이라는 표현만 있고 전체에서 어느 정도 비중을 담당했는지 알 수 없다. 섹션 서두에 "탐사 컨텐츠 전체 N종 중 4종을 담당했다" 한 줄로 정리하면 충분하다.

---

### 7. "기타 Chore" 섹션명 변경

"기타 Chore"는 포트폴리오 문서에 어울리지 않는 표현이다. "추가 구현 사항"으로 변경하고, 표에 나열된 4개 항목 중 설계 판단이나 어려움이 있었던 것이 있다면 한 줄씩 보강하는 것이 낫다.

---

### 8. AI 활용 방침 추가

문서 어디에도 AI 활용 여부에 대한 언급이 없다. 활용했다면 어떤 방식으로 활용했는지, 활용하지 않았다면 그에 대한 입장이라도 한 줄 명시하는 것이 좋다.
