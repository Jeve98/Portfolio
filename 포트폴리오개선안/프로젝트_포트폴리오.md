### 1. Thread safe Singleton — CRTP 패턴 적용

게임에서 사용하는 다수의 매니저 클래스마다 싱글톤 코드를 반복 작성하는 것은 유지 보수성을 낮춘다. **제네릭 베이스 클래스로 싱글톤 생성 로직을 분리**하고, 자신을 타입 파라미터로 넘기는 CRTP 패턴을 적용하여 매니저마다 독립적인 정적 인스턴스 필드를 갖게 했다. 이로써 `GameManager.Instance.StartGame()`처럼 캐스팅 없이 직접 접근 가능한 타입 안전성을 확보했다. 또한 `lock` 블록으로 상호 배제를 적용하여 추후 멀티 스레드 환경으로 확장 시 인스턴스 중복 생성을 방지했다.

```csharp
public class Singleton<T> : MonoBehaviour where T : MonoBehaviour
{
    private static T _instance;
    private static readonly object _lock = new object();

    public static T Instance
    {
        get
        {
            lock (_lock)  // 상호 배제
            {
                /* 싱글톤 생성 */
            }
        }
    }
}
```

에디터 계층 정리를 위해 매니저를 부모 오브젝트로 묶었더니 Unity 내부 제약으로 DontDestroyOnLoad가 동작하지 않는 문제가 발생했다. 부모 오브젝트에 싱글톤 컴포넌트를 추가하는 방법도 있었으나, 각 씬에서 `Find`로 매니저를 탐색·캐싱해야 하는 구조가 되어 싱글톤 패턴을 클라이언트 코드에서 수동으로 재구현하는 것과 다름없어 안전성이 낮아진다고 판단했다. **생성 시 부모 관계를 끊는 방식**으로 해결했다.

```csharp
lock (_lock)
{
    _instance = Object.FindAnyObjectByType<T>();
    if (_instance != null){
        MonoBehaviour mb = _instance as MonoBehaviour;
        if (mb.transform.parent != null)
            mb.transform.SetParent(null);
        /* 싱글톤 생성 */
    }
    else{ /* 싱글톤 생성 */ }
}
```

### 2. 세션 복구 시스템 — 상태 기반 씬 로드

**문제:** 웹 게임은 새로고침 시 씬이 재로드된다. 상태를 저장하지 않으면 다음 스테이지 정보를 미리 볼 수 있거나 방어전을 무한 반복하는 문제, 배치를 다시 해야 하는 불편함이 발생한다.

**해결:** 상태 변경 시점마다 유저 매니저에 현재 `GameState`를 저장하고, 씬 로드 시 이를 기반으로 적절한 씬으로 복구하도록 구현했다.

초기 구현은 switch문이었으나 상태가 추가될 때마다 switch를 수정해야 하는 **OCP 위반** 구조였다. **Dictionary 기반 상태-핸들러 매핑 방식**으로 리팩토링하여 새로운 상태 추가 시 딕셔너리에 항목만 추가하면 되도록 확장성을 확보했다.

```csharp
void Awake()
{
    Action recoverToBattle = () => StartCoroutine(RecoveryTransitionRoutine("Defense"));

    _recoveryHandlers = new Dictionary<GameState, Action>
    {
        { GameState.Preparation, recoverToBattle },
        { GameState.Battle,      recoverToBattle },
        { GameState.PostStage,   LoadPostStageScene },
    };
}

public void CheckAndRecoverySession()
{
    GameState lastState = GetLastSavedState();
    if (_recoveryHandlers.TryGetValue(lastState, out Action handler))
        handler();
}
```

### 3. 유닛 배치 시스템 — 단방향 동기화 + 상태 보존

**문제:** UI 배치 변경을 월드에 즉시 반영하면 유닛을 변경할 때마다 오브젝트를 생성/파괴해야 한다. 이 과정에서 버프·HP 등 컴포넌트 상태가 초기화된다.

**해결:** `UIGridController`에서 배치 상태를 저장하고, 배치 패널이 닫힐 때 `SyncDeploymentWithWorld()`를 호출하는 단방향 동기화 구조로 구현했다. 유닛 생성 시 고유 ID를 부여하고 UI 아이콘과 월드 오브젝트를 매핑하여, 재배치 시 오브젝트를 파괴하지 않고 이동시킴으로써 컴포넌트 상태를 보존했다.

```csharp
public void SyncDeploymentWithWorld()
{
    var currentDeployment = UIGrid.GetCurrentDeploymentWithIds();

    var unitsToRemove = _activeUnits.Keys
        .Where(name => !currentDeployment.ContainsKey(name)).ToList();
    foreach (var name in unitsToRemove)
        StartCoroutine(RetreatAndDestroy(_activeUnits[name]));

    foreach (var item in currentDeployment)
    {
        if (_activeUnits.TryGetValue(item.Key, out GameObject existing))
            StartCoroutine(TransitionUnit(existing));   // 배치 이동
        else
            StartCoroutine(DeployUnit(item));           // 신규 배치
    }
}
```

```csharp
float baseScale      = (unitRange / shieldRange) * 1.4f;
```

### 5. 오브젝트 풀 기반 스폰 시스템

압도적인 전쟁 경험을 위해 적게는 300마리, 많게는 1500마리 이상의 적 유닛이 필요했다. 웹 게임 특성상 브라우저가 점유 중인 리소스를 공유하므로 유닛 생성/파괴에 드는 GC 비용에 더 민감하게 대응할 필요가 있었다. 웨이브에서 등장하는 각 유닛의 40%를 풀에 미리 생성하고, 풀에서 가져오기 실패 시 **Pending Queue**에 쌓아뒀다가 다른 유닛이 반납될 때 꺼내는 방식으로 구현했다.

```csharp
int poolSize = Mathf.CeilToInt(enemyData.count * poolFillRatio);

private void SpawnEnemy(int unitId, int grade)
{
    GameObject obj = enemyObjectPool.Get(unitId);
    if (obj == null)
    {
        _pendingSpawn[unitId]++;    // 풀 고갈 시 pending
        return;
    }
    ApplyGrade(obj, unitId, grade);
}

private void OnEnemyReturnedHandler(int unitId)
{
    if (_pendingSpawn[unitId] <= 0) return;
    _pendingSpawn[unitId]--;
    SpawnEnemy(unitId, _unitGrades[unitId]);
}
```

### 7. 탐사 컨텐츠 구현 (N종 중 4종 담당)

다회차 플레이에서 매 회차를 다양하게 즐길 수 있도록 선택지 기반의 탐사 컨텐츠를 구현했다. 전체 탐사 컨텐츠 중 아래 4종을 담당했다.

**기근 (다회차 지속 디버프)**  
n번의 방어전 동안 소비 식량이 2배가 되는 지속성 디버프. 남은 횟수 차감 시점을 식량 소비 시점(방어전 시작)과 동기화하여 저장/로드 시점을 일원화했다. 새로고침 등 씬 재로드 시 횟수만 차감되거나 식량만 소비되는 버그를 구조적으로 방지하기 위함이다.

**마력 안개 (연출 효과 + 스탯 분기)**  
성공/실패에 따라 특정 스탯 버프 또는 디버프가 적용되고, 결과와 무관하게 다음 방어전에 안개 연출이 등장하는 이벤트. 연출과 스탯을 하나의 플래그로 묶으면 성공/실패/우회 세 경우의 분기 처리가 복잡해지기 때문에 두 채널을 분리하여 처리했다.

안개 연출은 Unity Particle System으로 구현했으나 기본 Alpha Blended Premultiply 쉐이더가 WebGL에서 지원되지 않아 안개가 렌더링되지 않는 문제가 발생했다. 빛의 영향을 받지 않으면서 WebGL에서 가벼운 Unlit 쉐이더 기반으로 머티리얼을 새롭게 제작하여 해결했다.

**인사 이동 (보유 병력 이전)**  
보유 병력 중 랜덤한 병과를 선택하여 다른 병과로 변경하는 이벤트. 대상 후보 선택, 타깃 선택, 실제 이전 수량을 보유 수량으로 클램프하는 세 단계로 구현했다.

```csharp
List<int> sourceIndices = new List<int>();
for (int i = 0; i < maxCount; i++)
    if (owned[i] > 0) sourceIndices.Add(i);

int sourceIndex = sourceIndices[Random.Range(0, sourceIndices.Count)];

List<int> targetIndices = new List<int>();
for (int i = 0; i < maxCount; i++)
    if (i != sourceIndex) targetIndices.Add(i);

int actualTransfer = Mathf.Min(settings.transferCount, owned[sourceIndex]);
```

**저주 정화 (웨이브 기반 엘리트 유닛 소환)**  
실패 시 다음 방어전에 엘리트 적 유닛을 추가로 등장시키는 이벤트. 엘리트 유닛을 특정 유닛으로 고정하면 웨이브 조합에 따라 위험도가 크게 달라지는 것을 로그 분석으로 확인했다. 이에 다음 웨이브 구성을 미리 확정한 뒤, 그 안에서 무작위로 유닛을 뽑아 엘리트로 대체하는 방식으로 구현했다.

### 8. 암호화 통신 — AES-GCM + RSA 세션키 교환

**문제:** 웹 게임은 브라우저 개발자 도구로 통신 내역을 쉽게 확인할 수 있다. 주요 데이터를 API로 받아 덮어쓰는 치팅 방지 구조를 사용했기 때문에 통신 보안이 더욱 중요했다.

| 방식 | 암복호화 속도 | 키 노출 위험 | 채택 여부 |
|:---:|:---:|:---:|:---:|
| 평문 전송 | — | 높음 | ✗ |
| 비대칭키 단독 (RSA) | 느림 | 낮음 | ✗ |
| 대칭키 단독 (AES) | 빠름 | 높음 (키 교환 문제) | ✗ |
| AES-GCM + RSA 세션키 교환 | 빠름 | 낮음 | **✓** |

게임 실행 시 신규 세션키를 생성하고 서버 공개키(RSA)로 암호화하여 교환한 뒤, 이후 통신은 AES-GCM으로 처리했다. IV를 매 요청마다 새로 생성하여 이전 암호문으로부터 데이터를 추측하는 것을 방지하고 AES-GCM의 무결성 보장을 활용했다.

```csharp
public static (string ivBase64, string dataBase64) Encrypt(string plaintext, byte[] key)
{
    byte[] iv = new byte[12];
    new SecureRandom().NextBytes(iv);  // 매 요청마다 새 IV 생성

    var cipher = new GcmBlockCipher(new AesEngine());
    cipher.Init(true, new AeadParameters(new KeyParameter(key), 128, iv));

    byte[] plaintextBytes = Encoding.UTF8.GetBytes(plaintext);
    byte[] output = new byte[cipher.GetOutputSize(plaintextBytes.Length)];
    int len = cipher.ProcessBytes(plaintextBytes, 0, plaintextBytes.Length, output, 0);
    cipher.DoFinal(output, len);

    return (Convert.ToBase64String(iv), Convert.ToBase64String(output));
}
```

### 2. 스폰 시스템 최적화 — 네트워크 트래픽 50% 감소

기존 스폰 데이터는 `position(x, y, z)` + `rotation(x, y, z)` 총 6개 값을 전송했다. 분석 결과 `position.y`, `rotation.x`, `rotation.z`는 게임 중 변하지 않는 고정값이었다. 살인마는 `position.y = 108f`, 생존자는 `position.y = 1f`로 고정하고 rotation은 Y축만 전송하도록 구조를 재설계하여 트래픽을 절반으로 줄였다.

```csharp
public (Vector3 position, Quaternion rotation) GetKillerSpawnData()
{
    Vector3 data = killerSpawnPoints[SelectedSpawnIndex];
    return (new Vector3(data.x, 108f, data.z), Quaternion.Euler(0, data.y, 0));
}

public (Vector3 position, Quaternion rotation) GetSurvivorSpawnData(int spawnOrder)
{
    int index = (SurvivorStartOffset + spawnOrder) % 5;
    Vector3 data = survivorSpawnPoints[SelectedSpawnIndex][index];
    return (new Vector3(data.x, 1f, data.z), Quaternion.Euler(0, data.y, 0));
}
```

### 4. 증강 시스템 — 추상 클래스 선택 근거

`Activate()`는 미구현 시 게임이 동작하지 않으므로 추상 함수로 강제화했다. `Awake()`는 프리팹에 활성화 상태로 잘못 추가되는 휴먼 에러를 막는 방어 코드이므로, 기본 동작은 유지하되 필요한 경우 오버라이드할 수 있도록 가상 함수로 두었다.

```csharp
public abstract class AbilityBase : NetworkBehaviour
{
    public abstract void Activate();

    protected virtual void Awake()
    {
        this.enabled = false;   // 방어 코드
    }
}
```

### 1. Min-Heap 기반 보스 패턴 시스템

**문제:** 랜덤 함수만 사용하면 강한 패턴이 연속으로 나오는 편차가 생기고, 쿨타임 기반은 특정 구간에 강한 패턴이 집중되는 사이클이 발생한다.

**해결:** 각 패턴에 우선순위를 부여하고 Min-Heap으로 관리하여 패턴이 균형 있게 섞이도록 했다. 쿨타임이 끝난 패턴만 힙에 삽입하므로 패턴 선택 시 상태 확인 절차도 제거된다. 삽입 시 O(log N)이지만 실제 패턴 수가 적어 무시할 수 있는 수준이다.

초기 switch문 구현을 패턴명을 Key로, 쿨타임을 Value로 갖는 Dictionary 기반 구조로 리팩토링하여 새 패턴 추가 시 딕셔너리에 항목만 추가하면 되도록 확장성을 확보했다.

```javascript
const BossPatterns = {
  coffin: {
    999: { key: "thunder",   cool: 2.5, init: 1  },
    1:   { key: "summons",   cool: 90,  init: 5  },
    2:   { key: "fireshoot", cool: 30,  init: 10 },
    3:   { key: "hassle",    cool: 40,  init: 30 },
  },
};

export function ChooseNextSkill(scene) {
  if (!BossInstance || !BossInstance.isInit) return;
  if (BossInstance.isAttack) return;

  const priority = BossInstance.nextPattern.pop();
  CastSkill(priority, scene);
}
```

```javascript
if ((this.playerStats.cutScene & (1 << this.sceneNumber)) == 0) {
```

### 5. Django REST API 서버 구축

SQLite3 기반 REST API 서버를 구축했다. SQLite3가 write-lock 기반의 동시성 한계를 갖는다는 것을 인지했으나, 구조 변경 전에 실제 게임에서 DB 쓰기 요청이 얼마나 발생하는지를 먼저 분석했다. 1인용 웹 게임이어서 플레이 중 대부분의 요청은 조회였고 쓰기는 회원가입과 저장 시점에만 발생했다. 또한 배포·테스트 인원이 SSAFY 서울 캠퍼스로 한정되어 동시 쓰기 최대치가 약 1000건 수준이었기 때문에 SQLite3로 충분히 대응 가능하다고 판단했다.

### 6. AI 생성 코드 구조화 — 역행 분석으로 버그 해결

팀원이 AI 코딩 도구로 생성한 대량의 비정형 코드에서 두 가지 버그를 해결했다.

**CASE 1 — 스킬 시스템:** 스킬 포인트 투자 시 특정 스킬에만 변경이 적용되지 않는 문제. 일부 스킬이 씬에서 직접 바인딩되어 있었고, 추상 클래스 상속 시 `base` 누락이 원인이었다. 각 스킬의 동작 흐름도를 작성하고 이상적인 구조와 주석을 포함한 코드를 문서화하여 팀원에게 리팩토링 방향을 제시했다.

**CASE 2 — 데이터 동기화:** 맵 이동 또는 재로그인 시 해금한 스킬이 초기화되는 문제. 코드량이 방대하여 전체 로그 분석이 불가했기에 관련 함수와 변수를 역방향으로 추적했다. Vue에서 Phaser를 로드할 때 API 데이터가 더미 계정 레벨 값을 덮어씌워야 하는데 레벨 필드에서만 해당 부분이 누락된 것이 원인이었다.

## AI 활용 방침

프로젝트 전반에서 AI를 적극 활용했다. 단순히 코드를 생성하는 것에 그치지 않고, 어떤 근거로 어떤 방식으로 동작하는지, 기존 코드와의 정합성과 연동성을 고려하여 프롬프팅하고 직접 검토한 후 사용하는 것을 원칙으로 했다. 프라가라흐 프로젝트에서 AI 생성 코드의 구조적 문제를 직접 분석하고 해결한 경험을 통해, AI 생성 코드를 맹신하지 않고 구조와 흐름을 파악하는 것의 중요성을 체감했다.
