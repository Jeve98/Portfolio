## 1. 첫인상 — 인사팀 관점

**긍정적 인상**
- 게임 기획 / 게임 프로젝트 두 컬럼으로 명확히 분리된 홈 화면 구조(`_layouts/home.html`)를 가지고 있다.
- 각 프로젝트 카드에 기간·인원·기술 스택이 표시되어 스크리닝 단계에서 빠르게 훑을 수 있다.
- 기획과 개발을 모두 보유한 신입 포트폴리오는 흔치 않다.
- 기획 문서 3개 중 2개(헤이터, 노룸베가)가 GDD 형식으로 전환되어, 형식적 완성도가 눈에 띄게 올라갔다.

**의문이 생기는 부분**
- 개발 프로젝트 3개가 전부 SSAFY 소속이다. 개인/사이드 프로젝트가 하나도 없다.
- 모든 프로젝트에 GitHub 코드 링크가 없다 (SSAFY 코드 비공개 규정상 불가피하나, 인사팀 입장에서는 "검증 불가"로 읽힌다).
- 펌블 기획서만 아직 에세이 형식으로 남아있어, 같은 포트폴리오 안에서 기획 문서 간 완성도 편차가 생겼다.

## 2. 개발 프로젝트별 평가

### 마네킹: 헌티드 몰 ★★★★☆

**무엇이 보이는가**
비대칭 PVP 멀티플레이 게임에서 기획부터 최적화까지 담당한 기록이 상세하다.
Occlusion Culling 선택 근거(LOD와 비교 후 비용 대비 효과로 판단), Jitter 원인 분석 및 RPC 동기화 일원화, 스폰 데이터 최적화(전송량 절반 감소)까지 구체적이다.
13fps → 63.6fps(약 300% 향상)라는 수치는 신입 포트폴리오에서 강력한 증거다.

**팀 리더가 볼 때 강점**
- 단순 구현이 아니라 왜 그 방법인지를 설명할 수 있다.
- `IInteractable` 인터페이스 vs 추상 클래스 선택 근거(C# 단일 상속 + NetworkBehaviour/MonoBehaviour 분리)가 구체적으로 서술되어 있다.
- 실제 배포 후 동시 접속 피드백이라는 현실 검증 단계가 있다.

**우려 사항**
- 6인 프로젝트에서 본인 기여 범위가 넓게 서술되어 있어 면접에서 직접 구현 범위를 검증하고 싶어질 수 있다.
- 코드가 발췌 형태(SSAFY 제약)라 전체 구현 능력을 판단하기 어렵다.

---

### 프라가라흐 ★★★☆☆

**무엇이 보이는가**
2인 프로젝트에서 프론트(Phaser), 백엔드(Django), 구조 재정비까지 담당한 기록이다.
Min-Heap 기반 보스 패턴 가중치 관리, 비트 연산 기반 컷신 시청 플래그 압축, 안전 구역 스폰 시스템이 흥미롭다.

**팀 리더가 볼 때 강점**
- 알고리즘/자료구조를 실제 문제에 적용한 사례(Min-Heap, 비트 연산)가 명확하다.
- AI가 생성한 비정형 코드를 구조화해 분석하고 팀원에게 공유한 경험은 실무적으로 유용하다 (Self-Introduce.md의 여러 자기소개서에서도 이 경험을 핵심 강점으로 반복 인용하고 있어, 본인 스스로도 가장 자신 있는 경험으로 인식하고 있음을 알 수 있다).
- 2인 프로젝트라 기여도가 상대적으로 명확하다.

**우려 사항**
- 마네킹 대비 완성도·규모가 작아 보인다.
- Phaser는 실무 연결 폭이 좁은 엔진이다.
- 배포 후 유저 반응 등 결과 임팩트가 없다.

---

### 헤이터 (개발) ★★★★☆

**무엇이 보이는가**
기획서를 직접 개발로 연결한 유일한 케이스다. Thread-safe CRTP Singleton, OCP 기반 리팩토링(switch → Dictionary 핸들러), AES-GCM+RSA 암호화 통신, WebGL 최적화까지 폭이 넓다.
드로우콜 3500→180, 메모리 60mb→15mb라는 수치가 있다.

**팀 리더가 볼 때 강점**
- 보안 전공 배경이 암호화 통신 구현으로 직접 이어진 케이스가 흥미롭다. 게임 클라이언트에서 통신 보안을 직접 설계한 신입은 드물다.
- OCP 위반을 인지하고 리팩토링한 사례는 코드 품질 감각을 보여준다.
- Pending Queue 기반 오브젝트 풀 스폰 시스템은 300~1500마리 단위 웨이브를 구조적으로 푼 사례다.

**우려 사항**
- 기획부터 개발까지 한 사람이 담당했다는 점이 강점이자 동시에, 각 영역의 깊이가 희석되어 보일 위험이 있다.
- 탐사 컨텐츠(15개 중 4개 구현, 일부 코드 주석 처리)는 완성도에 대한 의문을 남긴다.

## 3. 기획 문서별 평가

### 헤이터 (기획) ★★★★☆ (▲ GDD 전환 후 상향)

**무엇이 보이는가**
기존 디펜스 장르를 분석하고 "스테이지 간 지속성"이라는 차별점을 도출한 기획이다. Low Risk-Low Return(정찰) vs High Risk-High Return(탐사) 구조로 컨텐츠를 이원화했다.
이제 게임 개요 → 기획 배경/의도 → 게임 필라/코어 루프(흐름도 포함) → 컨텐츠 구조 → 시스템 명세 순의 GDD 구조를 갖추고 있다.

**기획 팀장이 볼 때 강점**
- 기획서가 실제 개발로 이어졌다는 것이 가장 강력한 증거다. 개발 단계의 `초기 기획 변경점` 표가 헤이터(개발) 글에 별도로 남아있어, 기획-개발 간 협의 프로세스가 실제로 작동했음을 보여준다.
- 재화(골드+식량 이원화) 설계에 전략적 고민이 담겨 있다.
- GDD 형식 전환으로 필라·코어 루프·시스템 명세가 명확히 구분되어, 형식만 봐도 기획 문서 작성 관행을 알고 있다는 신호를 준다.

**우려 사항**
- 밸런스 수치(병력 스탯, 재화 곡선 등)가 여전히 구체적인 숫자보다 정성적 표현 위주다. 구현 명세로 바로 쓰기엔 부족하다.

---

### 노룸베가 ★★★★☆ (▲▲ GDD 전환 + USP 명시로 2단계 상향)

**무엇이 보이는가**
RPG 5요소 분석 + 코로나 이후 게이머 행동 변화 + 던파 사례라는 데이터 기반 기획 배경, 보스 기믹(반전·선고·탐욕·저주) 설계, 시각화된 아이템 등급표(등급별 이미지 포함)를 갖췄다.
GDD 구조로 전환되며 USP가 "빠른 성장 체감과 보스레이드 카타르시스에 집중한 아이템 빌드형 RPG"로 한 줄 명시되었고, 게임 필라가 던닝/시즌제 보스레이드/적 유닛 정보 은닉 등으로 재구성되어 있다.

**기획 팀장이 볼 때 강점**
- 기획 배경이 개인 취향이 아닌 시장 데이터로 시작한다는 점이 가장 돋보인다.
- 장기 리텐션 전략(시즌제, 보스 기믹 사례, 패턴 다변화)까지 단계별로(필라=원칙 → 보스 시스템=시즌1 사례 → 장기 리텐션=사양) 구분해 서술한 구조가 일관적이다.
- 아이템 등급 표에 이미지를 직접 삽입해 시각적 완성도를 높였다 — 기획 문서를 커뮤니케이션 도구로 다룰 줄 안다는 신호다.

**우려 사항**
- 던전(구 던닝)·보스레이드·빌드 강화 루프의 수치 밸런스(드랍률, 강화 확률 등)가 아직 구체적이지 않다.
- 보스 기믹 4종 중 실제 구현 검증을 거친 것이 있는지(페이퍼 기획인지 프로토타입 검증을 거쳤는지) 문서만으로는 알 수 없다 — 면접에서 확인하고 싶은 지점이다.

### 펌블 ★★★☆☆ (변동 없음 — 유일하게 GDD 미전환)

**무엇이 보이는가**
TRPG + 로그라이크 + 세대 계승이라는 독특한 조합의 기획이다. 플래그 시스템에 의사 코드까지 첨부되어 있고, 남서 지역 12개 퀘스트 체인이 해금 조건과 함께 구체적으로 설계되어 있다.

**기획 팀장이 볼 때 강점**
- 플래그 기반 NPC 관계 영속성 설계에 의사 코드가 포함되어 있다 — 기획자가 "어떻게 구현될 수 있는지"를 이해하고 있다는 신호다.
- 영구 사망의 거부감을 세대 계승으로 전환한 유산 이벤트 설계가 참신하다.
- 캐릭터 스탯 체계(힘/민첩/지능/행운 + 특수 스탯 7종)가 구체적이다.

**우려 사항**
- 같은 포트폴리오 안의 헤이터·노룸베가는 GDD 형식인데 펌블만 에세이 형식으로 남아 있어, 셋을 나란히 보면 펌블이 상대적으로 미완성처럼 보인다.
- 다이스 수치, 스탯 성장 공식 등 밸런스 설계가 없다.
- 이 정도 규모(세대 계승 + 절차적 여정 생성 + TRPG 룰)를 몇 명이서 얼마의 기간에 구현 가능한지에 대한 검토가 없다.

## 4. 직군별 종합 평가

### 게임 클라이언트 개발자 신입 지원 시

**강점**
- 수치 기반 최적화 경험이 신입 수준을 넘는다. 마네킹·헤이터의 "프로파일링 → 원인 분석 → 수치 검증" 흐름은 경력자 면접에서도 통할 수준이다.
- 설계 패턴 적용(CRTP, OCP, 인터페이스 vs 추상 클래스)의 선택 근거를 항상 설명할 수 있다.
- Unity 멀티플레이(Photon Fusion)부터 WebGL, 웹 백엔드(Django, Spring)까지 스택 폭이 넓다.
- 기획 경험이 있어 기획자와의 협업/커뮤니케이션에서 강점을 가진다.

**약점**
- 개인 프로젝트가 없다. "SSAFY 팀 환경이 아니어도 혼자 만들 수 있는가"에 답할 근거가 포트폴리오 안에는 없다.
- 모든 프로젝트가 코드 비공개(SSAFY 제약)라 코드 품질을 직접 검증할 수 없고, GitHub 링크도 없다.
- Unity/C# 비중이 압도적이다. Unreal 경험은 `Self-Introduce.md`에서만 "블루프린트로 FPS MVP + 카메라 레일 연출 1건" 수준으로 언급될 뿐, 정작 포트폴리오 본문(`_posts`)에는 전혀 드러나지 않는다.

**예상 면접 질문**
1. "마네킹에서 Occlusion Culling 적용을 혼자 결정했나요? 팀원에게 어떻게 공유·설득했나요?"
2. "SSAFY 외에 혼자 만든 게임이나 프로토타입이 있나요?"
3. "코드 전문을 볼 수 없는데, 공개 가능한 개인 코드 샘플이 있나요?"
4. "Unreal 경험이 자기소개서에는 있는데 포트폴리오에는 왜 없나요?" — 이 질문은 면접관이 `Self-Introduce.md`까지 읽었을 때만 나오지만, 회사에 따라 자기소개서와 포트폴리오를 같이 보는 경우가 있어 대비가 필요하다.

### 게임 기획자 신입 지원 시

**강점**
- 시장/트렌드 분석을 기획 출발점으로 삼는 방법론이 일관된다(헤이터의 디펜스 장르 분석, 노룸베가의 코로나 이후 게이머 행동 변화·던파 사례).
- 기획 문서 3개 중 2개가 GDD 형식으로 전환되어, 형식적 전문성에서 이전 대비 크게 개선됐다.
- 개발 경험이 있어 구현 가능성을 고려한 기획이 가능하다는 차별점이 있다. 헤이터는 기획서가 실제 개발까지 이어진 유일한 케이스다.

**약점**
- 펌블이 아직 에세이 형식으로 남아 있어 3개 문서 간 완성도가 고르지 않다.
- 밸런스 수치(드랍률, 강화 확률, 다이스 곡선, 재화 성장식 등) 설계 근거가 세 문서 모두에서 약하다. 과금 모델·재화 밸런스 등 라이브 서비스형 경제 설계 경험도 보이지 않는다.
- 기획 문서 3개가 모두 "개인 기획"이다. 팀 단위 기획 리뷰/수정 이력을 경험했는지는 헤이터(개발) 글의 변경점 표 외에는 확인하기 어렵다.

**예상 면접 질문**
1. "헤이터 외 두 기획서(노룸베가, 펌블)는 실제로 구현해본 적이 있나요, 아니면 페이퍼 기획인가요?"
2. "노룸베가의 보스 드랍률이나 강화 확률처럼, 숫자로 설계해본 밸런스가 있나요?"
3. "펌블은 왜 다른 두 문서와 형식이 다른가요?" (GDD 미전환 상태이므로 면접관이 직접 비교하며 물어볼 가능성이 있다)

## 5. 포트폴리오 사이트 구조 및 노출 위생 (신규 — 2026-06-17 추가)

`_posts` 디렉토리를 전수 조사하는 과정에서, 홈 화면(`_layouts/home.html`)에는 보이지 않지만 실제로는 사이트에 빌드되어 외부에 노출될 수 있는 파일들을 발견했다. 홈 화면은 `post.category`가 `Game_Planning` / `Game_Development`인 글만 카드로 보여주는 구조이지만, `_config.yml`에 `jekyll-sitemap`과 `jekyll-feed` 플러그인이 활성화되어 있어 **카테고리가 비어 있는 글도 sitemap.xml과 RSS 피드를 통해 검색엔진·구독자에게 노출된다.** 채용 담당자가 GitHub 저장소를 직접 클론/열람하는 경우라면 `_posts` 폴더에서 곧바로 보일 수도 있다.

- **`Self-Introduce.md`**: 여러 회사(메이플스토리, 넥토리얼, 웹젠, 펄어비스, 컴투스, 다우기술, 네비웍스 등)에 제출한 자기소개서 원문을 모아둔 파일이다. "탈락" 표기가 포함된 지원 이력, 펄어비스 지원 시 본인이 직접 매긴 기술 자기평가(C#: 중, Unity: 중, Unreal: 하 등)가 그대로 들어있다. `layout`, `title` 프론트매터가 비어 있어 Jekyll이 정상적인 레이아웃 없이 페이지를 생성하거나 빌드 경고를 일으킬 가능성이 있고, 무엇보다 **다른 회사 탈락 이력과 자기 기술 수준에 대한 박한 자기평가가 공개 저장소에 그대로 노출**되는 것은 채용 과정에서 불리하게 작용할 수 있다. 면접관이 이 파일을 발견하면 "Unreal 경험이 사실상 거의 없다"는 점이 포트폴리오 본문보다 먼저 각인될 위험이 있다.
- **`2026-04-23-NoName.md`**: 제목이 "무제"이고 카테고리·이미지·요약이 모두 비어 있는, 정리되지 않은 아이디어 메모(오픈월드 MMORPG의 유니크 몬스터 컨셉 브레인스토밍)다. 완성된 기획 산출물이 아니라 초안 단계의 글이 실수로 `_posts`에 커밋되어 있는 상태로 보인다.
- **`Lanov.md`, `Styx.md`**: 전체 내용이 HTML 주석(`<!-- ... -->`)으로 감싸인 Jekyll 테마 기본 보일러플레이트(가상의 "Paul, a physics major" 더미 텍스트)가 그대로 남아있다. 실제 프로젝트 내용이 아니며, 저장소를 둘러보는 사람에게는 "정리되지 않은 레포"라는 인상을 줄 수 있다. (단, Self-Introduce.md의 자기소개서 본문에는 Styx가 3D 추리 게임 팀 프로젝트로 실제 언급되므로, 그 프로젝트 자체가 가짜라는 뜻은 아니고 — 포트폴리오용 글이 작성되다 만 채 방치된 것으로 보인다.)
- **`2026-01-13-Togethy.md`**: 전체가 HTML 주석 처리되어 있으나, 내용 자체는 실제 WebRTC 기반 스터디 플랫폼(Kurento/OpenVidu) 프로젝트다. Lanov/Styx와 달리 더미 텍스트가 아니라 미완성 초안이며, Kurento/OpenVidu 구현 상세 섹션이 비어 있다.

**권장 조치**
1. `Self-Introduce.md`는 공개 저장소(`_posts`)가 아닌 비공개 위치로 옮기거나, 최소한 탈락 이력·자기평가처럼 채용에 불리하게 읽힐 수 있는 부분을 제외한 형태로 정리하는 것을 권한다.
2. `NoName.md`는 카테고리를 지정해 정식 기획 문서로 발전시키거나, 완성 전까지는 `_posts`에서 제외(예: `_drafts`로 이동)하는 것이 안전하다.
3. `Lanov.md`, `Styx.md`의 더미 보일러플레이트는 삭제하거나, Styx를 실제로 포트폴리오에 올릴 계획이라면 내용을 채워 넣는 것이 좋다.
4. `Togethy.md`는 Kurento/OpenVidu 섹션을 완성한 뒤 주석을 해제해 정식 게시하거나, 완성 전까지 `_drafts`로 옮긴다.

## 6. 포트폴리오 전체 구조에 대한 평가

**잘 된 부분**
- 게임 기획 / 게임 프로젝트로 분리된 홈 화면 구조가 명확하다.
- 각 프로젝트 카드에 기간·기술 스택이 정리되어 있다.
- 프로젝트 문서가 결과 나열이 아니라 과정과 근거를 서술하고 있다.
- 기획 문서 3개 중 2개가 GDD 형식으로 전환되어, 같은 문서군 안에서의 형식적 일관성이 크게 개선됐다.

**보완이 필요한 부분**
- 펌블이 아직 GDD 미전환 상태라 기획 문서 3개의 완성도가 고르지 않다.
- SSAFY 외 활동(개인 프로젝트, 게임잼, 스터디)이 없어 자기 주도적 학습의 근거가 부족하다.
- 코드 저장소(GitHub)가 연결되어 있지 않다.
- `_posts`에 비공개로 두는 게 나을 자기소개서 모음과 미완성 초안이 그대로 커밋되어 있어, 사이트 노출 위생 측면의 리스크가 있다 (5절 참고).
