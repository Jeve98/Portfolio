## 프로젝트별 평가

### 마네킹: 헌티드 몰 ★★★★☆ (가장 강한 카드)

**잘한 것:**
- **수치로 말한다** — 13fps → 63.6fps (약 300% 향상), 네트워크 트래픽 50% 감소. 신입 포트폴리오에서 이런 수치 근거 제시는 흔하지 않아서 바로 눈에 띔
- **설계 판단 근거를 언어로 설명한다** — "상호작용은 수평 확장이라 인터페이스, 증강은 수직 확장이라 추상 클래스" 같은 서술은 단순 구현자가 아닌 설계자적 사고를 보여줌
- **멀티플레이 실전 경험** — Photon 기반 Jitter 발생 → 원인 분석 → 해결 과정을 서술한 것은 팀 리더 입장에서 실전 감각 있다고 읽힘
- **플레이 영상 있음** — SSAFY 내 배포 + 유튜브 링크 첨부로 실제 동작 확인 가능
- AI 활용에 대해 방어적으로 설명하지 않고 "근거 있는 프롬프팅"이라고 태도를 명시한 것도 긍정적

**부족한 것:**
- GitHub 소스코드 링크 없음 (SSAFY 저작권 제약으로 공개 불가 — 단, 이 이유가 포트폴리오에 명시되어 있지 않음)
- 6인 팀에서 본인 기여 비중이 얼마인지 불명확

### 헤이터 ★★☆☆☆ → 완성 후 재평가 예정

**현재 상태:**  
기획 단계(2일)는 완료되었고, 현재 개발이 한창 진행 중이다.  
완성 후 개발 포트폴리오로 추가될 예정이며, 기획 페이지는 GDD 형태로 정비할 계획이다.

**현재 기획 페이지 기준 평가:**

잘한 것:
- "현재 행동이 미래 스테이지에 영향을 준다"는 기획 핵심 아이디어가 명확하고 차별점이 있음
- 유닛 간 상성과 적 면역 설계가 단순 숫자 밸런스가 아닌 구조적으로 설계됨

현재 기준 부족한 것:
- 기획 단계 포스트만 있어서 개발 완성 전까지는 텍스트 기획서 수준으로 읽힘
- 플로우 시각 자료, UI 설계 등 보강 필요

**완성 후 개발 포트폴리오 추가 시 체크리스트:**
- [ ] 플레이 영상 (유튜브 링크)
- [ ] 담당 기능 및 기술적 선택 근거 서술
- [ ] 성능 수치 또는 문제 해결 사례
- [ ] SSAFY 외 개인 프로젝트이므로 GitHub 공개 가능 여부 확인
- [ ] 기획 페이지와 상호 링크 연결 (아래 참고)

**헤이터 기획 페이지 — 개발 완성 후에도 유지할 것**

기획 페이지는 개발 완성 후에도 삭제하지 않고 그대로 유지한다.  
개발 과정에서 수정되거나 추가된 내용이 많기 때문에 기획 원안과 실제 결과물을 분리해서 보여주는 것이 오히려 강점이 된다.

신입 포트폴리오 대부분은 완성된 결과물만 보여준다. 기획서와 개발 포스트를 함께 두면 채용 담당자 입장에서 이렇게 읽힌다:
> "기획도 할 줄 알고, 실제로 만들기도 했고, 만들면서 뭐가 달라졌는지도 인식하고 있다."

특히 기획자 직군에서는 "기획대로 안 되는 걸 아는 기획자"를 선호한다. 처음 기획이 개발 과정에서 바뀌는 건 당연한 일이고, 그걸 자연스럽게 보여주는 구성은 현장 감각이 있다는 인상을 준다.

**두 페이지 연결 방법:**
- 기획 페이지 하단: `이 기획을 바탕으로 개발된 프로젝트 → [헤이터 개발 포스트 링크]`
- 개발 페이지 상단 개요 표: `기반 기획 문서 → [헤이터 기획 포스트 링크]`
- 개발 페이지 내 "기획과 달라진 점" 섹션을 짧게 추가  
  → "초기 기획에서는 X였는데 개발 중 Y로 변경했다, 이유는 Z" 수준으로 충분

## 전체 약점 및 개선 포인트

### 1. GitHub 없는 이유를 포트폴리오에 명시해야 함
SSAFY 저작권 제약으로 코드를 공개할 수 없다는 것은 타당한 이유지만, **채용 담당자는 그 이유를 모른다.** "SSAFY 프로젝트 특성상 전체 코드 공개 불가, 핵심 코드 발췌 첨부" 같은 한 줄을 각 프로젝트 페이지에 명시해두면 오히려 신뢰감을 줌. 안 쓰면 숨기는 것처럼 보임.

### 2. 메인 페이지에 역량 키워드가 없음
"모두에게 추억으로 남을 게임을 개발합니다"는 태도로서는 좋지만, 인사팀은 **"이 사람이 뭘 할 수 있는가"**를 첫 화면에서 바로 읽고 싶어 함. 예시:
> Unity / C# 개발 · 게임 시스템 기획 · 멀티플레이 네트워크 최적화 경험

이런 식의 스킬 요약이 메인에 있어야 함.

### 3. 헤이터 — 개발 완성 전까지는 현재 상태 유지, 완성 후 개발 탭에 추가
현재 개발 진행 중이므로 완성 후 개발 포트폴리오로 정식 추가할 것.  
그 전까지 기획 페이지는 "기획 컨셉 문서"임을 명시하여 완성 기획서처럼 오해받지 않도록 한다.  
완성 후에는 기획 포스트 4개 + 개발 포스트 3개로 각 직군 제출용 볼륨이 갖춰진다.

### 4. 포트폴리오 제출 전략 — 직군별 섹션 페이지만 제출
기획 섹션과 개발 섹션이 나뉘어 있지만, 기존에는 두 섹션이 모두 보이는 메인 페이지를 함께 제출했다.  
헤이터 완성 후 개발 3개, 기획 4개로 각 직군 볼륨이 갖춰지면 **직군에 맞는 섹션 페이지 URL만 제출**하는 것이 유리하다.

| 지원 직군 | 제출 페이지 |
|----------|------------|
| 게임 개발자 | 개발 섹션 페이지 URL |
| 게임 기획자 | 기획 섹션 페이지 URL |
| 소규모/인디 (기획+개발 겸직 명시 공고) | 메인 페이지 URL (전체 노출) |

이유: 채용 담당자는 포트폴리오를 빠르게 읽는다. 개발자 채용 담당자에게 기획서 여러 개가 같이 보이면 포지션이 불명확하다는 인상을 준다. 관련 없는 것을 보여주지 않는 것이 더 전략적이다.

### 5. 기획서가 GDD 포맷이 아님 (아래 별도 설명 참고)

### 6. 개발/기획 섹션 페이지에 자기소개가 없음
메인 페이지에는 짧은 자기소개가 있지만, 개발 페이지와 기획 페이지에는 없다.  
직군별 섹션 URL을 직접 제출하는 전략을 쓸 경우, 채용 담당자는 메인을 거치지 않고 해당 페이지에 바로 들어온다.  
자기소개 없이 프로젝트 목록만 보게 되면 이 사람이 누구인지 파악할 맥락이 없다.

각 섹션 페이지 상단에 **해당 직군에 맞게 다듬은 짧은 자기소개**를 추가해야 한다.  
메인 자기소개를 그대로 복붙하는 것이 아니라, 개발 페이지는 개발 역량 중심으로, 기획 페이지는 기획 역량 중심으로 각각 다르게 작성한다.  
(예시는 별도 파일 `섹션페이지_자기소개_예시.md` 참고)

### 7. 학력/이수 이력이 없음
포트폴리오에 교육 배경이 전혀 없음. SSAFY 수료 이력만이라도 명시하면 신뢰도가 올라감. 인사팀은 서류 단계에서 이걸 기준으로 걸러내는 경우가 있음.

## GDD(게임 디자인 문서)란?

GDD(Game Design Document)는 게임 기획자가 실무에서 작성하는 공식 기획 문서 형식이다.  
현재 포트폴리오의 기획 페이지들은 분량은 충분하지만 **블로그 포스트 스타일**에 가깝고, GDD 형태가 아니기 때문에 기획자 직군 지원 시 "실무 문서 작성 경험이 있는가"라는 질문에 명확한 답이 되지 않는다.

### GDD의 기본 구성 요소

| 섹션 | 설명 | 현재 포트폴리오 |
|------|------|----------------|
| **게임 개요** | 한 문단으로 게임 핵심 설명 (엘리베이터 피치) | 일부 있음 |
| **타겟 플레이어** | 연령, 성별, 플레이 습관, 참조 게임 | 없음 |
| **핵심 게임플레이 루프** | 플레이어가 반복하는 핵심 행동 사이클 | 일부 있음 |
| **기능 목록** | 구현할 기능의 우선순위 목록 (Must/Should/Could) | 없음 |
| **시스템 설계** | 각 시스템의 규칙, 수치, 상호작용 명세 | 노룸베가/펌블에 있음 |
| **UI/UX 흐름** | 화면 전환 플로우, 주요 UI 와이어프레임 | 펌블 일부만 |
| **아트 디렉션** | 참조 이미지, 분위기, 색감 방향 | 없음 |
| **개발 일정** | 마일스톤, 기능별 예상 개발 기간 | 없음 |
| **리스크 관리** | 구현 난이도가 높은 부분과 대안 | 없음 |
| **경쟁작 분석** | 유사 게임과의 차별점 명시 | 일부 있음 |

### 기획자로 지원할 경우 개선 방향

노룸베가 또는 펌블 중 하나를 골라 위 구성 요소를 갖춘 정식 GDD 형태로 다듬는 것을 권장한다.  
분량을 줄이고 구조를 갖추는 것이 분량을 늘리는 것보다 훨씬 효과적이다.

## 직군별 채용 담당자가 느끼는 것

**개발자 신입 지원 시 (인사팀 시각):**
기술 스택이 다양하고 성능 최적화 수치와 플레이 영상이 있어 서류 통과 가능성 있음. 단, GitHub 부재에 대한 설명이 없으면 개발팀 리더가 불안해할 수 있음.

**개발자 신입 지원 시 (팀 리더 시각):**
설계 판단 근거를 언어로 표현하는 능력은 높이 살 것. 네트워크 최적화와 멀티플레이 경험도 플러스. 코드 발췌와 수치 근거가 있어서 SSAFY 제약 하에서는 최선을 다한 구성.

**기획자 신입 지원 시 (인사팀 시각):**
기획 분량은 충분하지만 플레이 가능한 결과물이 없어서 "기획만 잘 쓰는 사람 아닌가?" 의구심이 생길 수 있음.

**기획자 신입 지원 시 (팀 리더 시각):**
트렌드 분석과 시스템 간 연결 설계 능력은 기획자로서 가능성 있음. 단, GDD 포맷으로 다듬고 타겟 플레이어 정의와 경쟁작 분석을 보강해야 설득력이 생김.

## PPT / PDF 제출 전략

URL이 아닌 파일 제출만 허용하는 공고의 경우, 기존 웹 포트폴리오를 그대로 PDF로 변환하면 웹 레이아웃과 어색하게 맞물려 완성도가 떨어진다.
웹 포트폴리오와 별도로 **슬라이드 포맷을 상정한 PPTX/PDF를 따로 제작**하는 것이 맞다.

### 슬라이드 구성 원칙

| 원칙 | 설명 |
|------|------|
| 슬라이드당 1개 핵심 | 한 슬라이드에 하나의 메시지만 담는다 |
| 수치는 크게 | Before/After 수치는 슬라이드 중앙에 크게 배치 |
| 코드는 짧게 | 핵심 구조만 발췌, 전체 코드 붙여넣기 금지 |
| 텍스트 최소화 | 웹 포트폴리오의 긴 문장을 그대로 옮기지 않는다 |
| 일관된 테마 | 배경·강조색·폰트를 전 슬라이드에 통일 |

### 단일 프로젝트 슬라이드 구성 (8슬라이드 기준)

| 슬라이드 | 내용 |
|---------|------|
| 1. 표지 | 프로젝트명, 기간, 팀, 기술 스택, 역할 요약 |
| 2. 게임 개요 | 기획 의도, 프로젝트 정보 |
| 3. 담당 역할 | 역할 전체를 카드 형식으로 한눈에 |
| 4. 핵심 구현 1 | 문제 → 분석 → 결과 (3단 구성) |
| 5. 핵심 구현 2 | Before/After 수치 중심 |
| 6. 설계 판단 | 기술 선택 근거 (비교 카드 형식) |
| 7. 트러블슈팅 | 문제 발생 → 원인 → 해결 → 결과 흐름 |
| 8. 성과 요약 | 핵심 수치 3개 + 경험 키워드 |

### 예시 파일

`포트폴리오개선안\마네킹_포트폴리오.pptx` — 마네킹 프로젝트 8슬라이드 예시 (다크 테마)
