# 포트폴리오 분석 — 전연욱

> 분석 기준: 게임 개발자 / 게임 기획자 신입을 뽑는 회사의 인사팀 및 팀 리더 시각  
> 분석일: 2026-06-01  
> 분석 대상: 마네킹, 프라가라흐, 헤이터(개발), 헤이터(기획), 펌블, 노룸베가

---

## 1. 첫인상 — 인사팀 관점

포트폴리오를 처음 열었을 때 받는 인상이 최종 판단에 생각보다 큰 영향을 미친다.

**긍정적 인상**
- 개발 프로젝트 3개 + 기획 문서 3개가 분리된 섹션으로 정리되어 있어 구조가 명확하다.
- 각 프로젝트마다 기간, 인원, 기술 스택이 카드에 표시되어 한눈에 파악된다.
- 기획과 개발을 겸비한 구성이 희소하다. 신입 포트폴리오에서 이 조합은 눈에 띈다.

**의문이 생기는 부분**
- 모든 개발 프로젝트가 SSAFY 소속이다. 개인 프로젝트가 단 하나도 없다.
- 기획 문서가 에세이 형식이다. GDD에 익숙한 회사의 기획 팀장이라면 바로 알아챈다.

---

## 2. 개발 프로젝트별 평가

### 마네킹: 헌티드 몰 ★★★★☆

**무엇이 보이는가**
비대칭 PVP 멀티플레이 게임에서 기획부터 최적화까지 담당한 기록이 상세하다.  
Occlusion Culling 선택 근거(LOD와 비교 후 비용 대비 효과로 판단), Jitter 원인 분석 및 동기화 일원화, 스폰 데이터 최적화(전송량 절반 감소)까지 구체적이다.  
13fps → 63fps라는 수치는 신입 포트폴리오에서 매우 강력한 증거다.

**팀 리더가 볼 때 강점**
- 단순 구현이 아니라 왜 그 방법인지를 설명할 수 있다.
- 인터페이스 vs 추상 클래스 선택 근거가 구체적으로 서술되어 있다. 설계 사고력이 있다는 신호다.
- 실제 배포 후 50명 동시 접속이라는 현실 피드백이 있다.

**우려 사항**
- 6인 프로젝트에서 본인의 기여 범위가 넓게 서술되어 있어, 실제로 얼마나 직접 구현했는지 면접에서 검증하고 싶어질 수 있다.
- 살인마 진영 기능 구현 부분의 코드가 발췌 형태라 전체 구현 능력을 판단하기 어렵다. (SSAFY 제약)

---

### 프라가라흐 ★★★☆☆

**무엇이 보이는가**
2인 프로젝트에서 프론트(Phaser), 백엔드(Django), 구조 재정비까지 담당한 기록이다.  
Min-Heap 기반 보스 패턴 설계, 비트 연산 DB 최적화, 안전 구역 스폰 시스템이 흥미롭다.

**팀 리더가 볼 때 강점**
- 알고리즘/자료구조를 프로젝트에 실제로 적용한 사례(Min-Heap, 비트 연산)가 있다. 알고리즘을 아는 것과 쓸 줄 아는 것은 다르다.
- AI 생성 비정형 코드를 분석하고 재정비한 경험은 현실적으로 매우 유용한 역량이다.
- 2인이라 본인 기여도가 상대적으로 명확하다.

**우려 사항**
- 마네킹에 비해 전체적인 완성도와 규모가 작아 보인다.
- Phaser라는 비주류 엔진 경험이 실무에서 직접 연결되는 회사는 제한적이다.
- 프로젝트 결과물의 임팩트(유저 반응, 배포 후 피드백)가 없다.

---

### 헤이터 (개발) ★★★★☆

**무엇이 보이는가**
기획서를 직접 개발로 연결한 유일한 케이스다. Thread-safe CRTP Singleton, OCP 기반 리팩토링, AES-GCM 암호화 통신, WebGL 최적화까지 폭이 넓다.  
드로우콜 3500→180, 메모리 60mb→15mb라는 수치가 있다.

**팀 리더가 볼 때 강점**
- 보안 전공 배경이 암호화 통신 구현으로 직접 이어진 케이스가 흥미롭다. 게임 클라이언트에서 통신 보안을 직접 설계한 신입은 드물다.
- OCP 위반을 인지하고 switch → Dictionary 핸들러로 리팩토링한 사례는 코드 품질에 대한 감각을 보여준다.
- Pending Queue 기반 스폰 시스템은 문제를 구조적으로 푼 사례다.

**우려 사항**
- 기획에서 시작해 개발까지 담당했다는 점이 강점이기도 하지만, 한 사람이 너무 많은 역할을 한 것처럼 읽힐 수 있다. 각 영역의 깊이가 희석되어 보일 위험이 있다.
- 일부 탐사 컨텐츠 코드가 주석 처리되어 있다. 완성도에 대한 의문이 생긴다.

## 3. 기획 문서별 평가

### 헤이터 (기획) ★★★★☆

**무엇이 보이는가**
기존 디펜스 장르를 분석하고 "스테이지 간 지속성"이라는 차별점을 도출한 기획이다.  
Low Risk-Low Return(정찰) vs High Risk-High Return(탐사) 구조로 컨텐츠를 이원화한 설계가 논리적이다.

**기획 팀장이 볼 때 강점**
- 기획서가 실제 개발로 이어졌다. 종이 기획이 아니라는 것이 가장 강력한 증거다.
- 개발 중 기획 변경 사항을 문서화하고 팀 승인을 거친 프로세스가 기술되어 있다. 실무 감각이 있다.
- 재화(골드+식량 이원화) 설계에 전략적 고민이 담겨 있다.

**우려 사항**
- 기획서 형식이 GDD가 아닌 서술형이다.
- 밸런스 수치가 없다. "낮다/높다"로 표현된 부분이 많아 구현 명세로 쓰기엔 부족하다.

---

### 노룸베가 ★★★☆☆

**무엇이 보이는가**
RPG 5요소 분석 + 코로나 이후 게이머 행동 변화 + 던파 사례라는 데이터 기반 기획이다.  
보스 기믹(반전·선고·탐욕·저주) 설계가 구체적이고 아이템 등급 시스템이 시각화되어 있다.

**기획 팀장이 볼 때 강점**
- 기획 배경이 개인 취향이 아닌 시장 데이터로 시작한다. 이게 이 기획 문서에서 가장 돋보이는 부분이다.
- 장기 리텐션 전략(시즌제, 도감, 패턴 다변화)까지 포함한 것이 단순 컨셉 문서와 다르다.

**우려 사항**
- GDD 형식이 아니다. 게임 필라, 코어 루프, 시스템 명세가 명시적으로 구분되지 않는다.
- USP가 명확하지 않다. "보스레이드 중심 RPG"는 장르 설명이지 차별점이 아니다.
- 보스 기믹 중 반전[시점]은 "기술적 한계 확인이 필요"라고 명시되어 있어 확정 기획이 아님을 드러낸다.

---

### 펌블 ★★★☆☆

**무엇이 보이는가**
TRPG + 로그라이크 + 세대 계승이라는 독특한 조합의 기획이다.  
플래그 시스템에 코드 예시까지 첨부한 점이 개발 이해도를 보여준다.

**기획 팀장이 볼 때 강점**
- 플래그 시스템 설계에 의사 코드가 포함되어 있다. 기획자가 "이 기능은 어떻게 구현할 수 있다"를 이해하고 있다는 신호다.
- 유산 이벤트(영구 사망의 거부감을 세대 계승으로 전환)라는 설계가 참신하다.
- 남서 지역 여정 해금 트리가 구체적으로 설계되어 있다.

**우려 사항**
- GDD 형식이 아니다.
- 시스템 규모에 비해 밸런스 설계가 없다. (다이스 수치, 스탯 성장 공식 등)
- 구현 가능성 검토가 부족하다. 이 규모를 몇 명이 얼마나 만들 수 있는지에 대한 고려가 없다.

---

## 4. 직군별 종합 평가

### 게임 개발자 신입 지원 시

**강점**
- 수치 기반 최적화 경험이 신입 수준을 뛰어넘는다. 마네킹과 헤이터의 프로파일링 → 원인 분석 → 수치 검증 흐름은 경력자에게도 강한 인상을 준다.
- 설계 패턴 적용(CRTP, OCP, 인터페이스/추상 클래스)의 근거를 설명할 수 있다.
- Unity 멀티플레이(Photon PUN)부터 WebGL, 웹 백엔드(Django, Spring)까지 폭이 넓다.
- 게임 기획 경험이 있어 기획자와의 소통에서 강점을 가진다.

**약점**
- 개인 프로젝트가 없다. "SSAFY 팀 환경이 아닌 혼자서 만들 수 있는가"라는 질문에 답할 근거가 없다.
- 모든 프로젝트에서 코드 전문 비공개(SSAFY 제약)라 코드 품질을 직접 검증하기 어렵다. GitHub 링크가 없다.
- Unity/C# 집중도가 높다. Unreal 경험은 Self-Introduce에만 언급되어 있어 포트폴리오에서 보이지 않는다.

**예상 면접 질문**
1. "마네킹에서 Occlusion Culling 적용을 혼자 결정했나요? 팀원을 어떻게 설득했나요?"
2. "SSAFY 외에 혼자 만든 게임이 있나요?"
3. "코드 전문을 볼 수 없는데, GitHub에 공개 가능한 개인 프로젝트가 있나요?"

---

### 게임 기획자 신입 지원 시

**강점**
- 시장/트렌드 분석을 기획 출발점으로 삼는 방법론이 일관되게 나타난다. 개인 취향이 아닌 근거로 기획한다.
- 개발 경험이 있어 구현 가능성을 고려한 기획이 가능하다는 차별점이 있다.
- 헤이터처럼 기획서가 실제 개발로 이어진 케이스가 있다.

**약점**
- GDD 형식이 아니다. 기획 문서의 전문성이 형식적으로 드러나지 않는다.
- 밸런스 설계, 수치 근거, 경제 시스템 설계 경험이 보이지 않는다. 게임 경제(과금 모델, 재화 균형)나 레벨 디자인 경험도 없다.
- 기획 문서 3개가 모두 "개인 기획"이다. 팀 기획 프로세스(기획서 리뷰, 수정 이력 등)를 경험했는지 알 수 없다.
- UI/UX 목업이 일부 있지만 전체적으로 비주얼 설계 능력은 드러나지 않는다.

**예상 면접 질문**
1. "GDD를 작성해본 경험이 있나요?"
2. "기획한 내용이 개발 과정에서 변경된 사례가 있나요? 어떻게 조율했나요?"
3. "노룸베가의 아이템 밸런스는 어떻게 설계했나요? 수치 근거가 있나요?"

## 5. 포트폴리오 전체 구조에 대한 평가

**잘 된 부분**
- 개발/기획을 분리한 섹션 구조가 명확하다.
- 각 프로젝트 카드에 기간·기술 스택이 정리되어 있다.
- 프로젝트 문서가 단순 결과물 나열이 아니라 과정과 근거를 서술하고 있다.

**보완이 필요한 부분**
- 기획 문서 3개가 GDD 형식이 아니다. 형식 자체가 전문성의 신호다.
- SSAFY 외 활동(개인 프로젝트, 게임잼, 스터디)이 없어 자기 주도적 학습의 근거가 부족하다.
- 코드 저장소(GitHub)가 연결되어 있지 않다. 채용 팀은 코드를 직접 보고 싶어한다.

## 6. 직군별 한 줄 총평

| 직군 | 총평 |
|------|------|
| 게임 클라이언트 개발자 | 수치 성과와 설계 사고력은 강력하다. 개인 프로젝트 부재와 GitHub 비공개가 아쉬움 |
| 게임 기획자 | 분석적 기획 방법론은 차별점이다. GDD 형식 미흡과 밸런스 설계 경험 부재가 감점 |
| 기획+개발 겸직 지원 | 두 역량을 겸비한 구성 자체가 희소하다. 이 포트폴리오의 가장 강한 포지션 |
